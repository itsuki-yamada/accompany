# Accompany を止めたりターミナルを閉じたりしたら、端末を閉じたときと同じく SIGHUP を送る

- 日付: 2026-10-29
- ストーリー: #197

## 背景

PTY のコマンド（シェル）は `Bun.spawn` の `terminal` で起動し、別のセッション（setsid）で動く。Accompany を止めるとき（合図の処理 → `Workspace.killAll`）とタブを閉じるとき（`removeTerminal`）は、どちらも `TerminalSession.kill` からシェルに `proc.kill()`（SIGTERM）を送っていた。

対話シェル（zsh・bash）は SIGTERM を無視する。止めるときにシェルと前面のコマンドが終わっていたのは、Accompany が終わって PTY が閉じ、カーネルが SIGHUP を送っていたからだった。そのため次のことが起きていた。

- 前面のコマンドが SIGHUP を受けて片付けるときには、もう端末に書けない（PTY のもう一方が閉じている）
- タブを閉じても、シェルと前面のコマンドが残る（Accompany が動いている間は PTY が閉じないため）

利用者から「終了したときに SIGKILL を送る必要はないか」と聞かれ、SIGKILL ではなく、端末を閉じたときと同じ SIGHUP を明示的に送ることにした。次の点で判断が要った。

1. どのプロセスに送るか
2. 送ったあと、どれだけ待つか
3. 止めるときの保存（[ADR 151](151-restore-cwd.md)）や、起動役（[ADR 191](191-run-on-bun.md)）との関係

## 検討した案（どこに送るか）

- **A**: シェルの pid だけに SIGHUP を送る。bash と zsh は SIGHUP を受けると自分のジョブにも SIGHUP を送るので、多くの場合はこれで足りる。ただし、ジョブに送らないシェル（`sh` / dash、zsh の `NO_HUP`）や、起動時のコマンドがシェルでないとき（`accompany -- <コマンド>` で、そのコマンドが子を前面に出す）は、前面のコマンドに届かない
- **B**: シェルのプロセスグループと、端末の前面のプロセスグループ（tcgetpgrp 相当）の両方に SIGHUP を送る。端末を閉じたときにカーネルがすること（セッションのリーダーと前面のプロセスグループへの SIGHUP）に近い
- **C**: B に加えて、待っても終わらなければ SIGKILL を送る。確実に止まるが、SIGHUP を無視するもの（`nohup`・`disown`）まで止めてしまい、ふつうの端末と振る舞いが違う

B を選ぶ。

## 決定

- **送る合図**: SIGHUP。SIGTERM と SIGKILL は送らない
- **送る先**:
  - シェル（起動したコマンド）のプロセスグループ。シェルはセッションのリーダーなので、プロセスグループの番号は pid と同じ
  - 端末の前面のプロセスグループ。[ADR 70](70-agent-detection.md) で前面のコマンドを見分けるのに使っている ps（`ps -o tpgid= -t <端末>`）で、送る直前に調べ直す。調べるのは 500 ミリ秒までで、調べられなければ最後に見分けたときのものを使う。シェルと同じなら 1 回だけ送る。1 以下の番号には送らない
  - 前面のプロセスグループは、送る前に調べる。シェルが先に終わると、端末がセッションから外れて前面のプロセスグループが分からなくなるため
- **待ち方**:
  - シェルが終わり、前面のプロセスグループにプロセスがいなくなるのを待つ（`kill(-pgid, 0)` を 20 ミリ秒おきに確かめる）。前面のプロセスグループを調べる時間を含めて、1 秒までにする
  - Accompany を止めるときは、全部のターミナルを並行に待ってから終わる。タブを閉じるときは待たない（閉じる操作はすぐに終わり、コマンドは後ろで終わる）
  - 1 秒たっても終わらないもの（SIGHUP を無視する、片付けに時間がかかる）は残したまま Accompany が終わる。そのあとは、これまでどおり PTY が閉じたときにカーネルが SIGHUP を送る
- **順番**: 止めるときは、これまでどおり先に画面とカレントディレクトリを保存し（最大 3 秒、ADR 151）、そのあとで SIGHUP を送る。止まるまでは最大でおよそ 4 秒になる
- **起動役との関係**: npm の起動役（`npm/accompany/bin/accompany.js`）と bunx は、受けた合図を Accompany に伝え、Accompany が終わるまで待つ。Accompany は二度目以降の合図を無視する。起動役には待つ時間の上限がないので、Accompany が待つ時間が延びても、起動役が先に終わって Accompany が取り残されることはない。VS Code の拡張（[ADR 183](183-liveshare-extension.md)）は SIGTERM を送って 5 秒で止まらなければ SIGKILL を送るが、止まるまでの最大（およそ 4 秒）はその内に収まる

## 理由

- **SIGHUP にする理由**: 端末を閉じたときにコマンドが受け取るのは SIGHUP で、シェルやエディタ、エージェントの多くは SIGHUP を受けたときの片付け（履歴の保存、一時ファイルの削除など）を持っている。対話シェルは SIGTERM を無視するので、SIGTERM ではシェルが終わらない
- **SIGKILL を送らない理由**: 片付けの機会を奪う。また、`nohup` や `disown` で SIGHUP を無視させたものは、端末を閉じても残すために利用者がそうしている。ふつうの端末と同じ振る舞いにする
- **前面のプロセスグループにも送る理由**: シェルがジョブに送らない場合や、起動時のコマンドがシェルでない場合にも、前面のコマンドに届くようにする。bash と zsh では前面のコマンドが 2 回受け取ることがあるが、ふつうの端末を閉じたときも、カーネルとシェルの両方から届くことがある
- **ps で調べる理由**: `Bun.spawn` の `terminal` は前面のプロセスグループを返す API を持たない。ADR 70 で前面のコマンドを見分ける仕組みがすでにあり、macOS と Linux のどちらでも動く
- **待つ理由**: 待たずに Accompany が終わると PTY が閉じ、前面のコマンドが片付けるときに端末へ書けない（「保存しました」などの表示や、端末のモードを戻す出力が失敗する）。シェルも、終わる前に PTY が閉じると、履歴の保存などの途中で 2 回目の SIGHUP を受ける
- **1 秒にする理由**: シェルとふつうのコマンドは、SIGHUP を受けると数十ミリ秒で終わる。止めるときの保存（最大 3 秒）と合わせて、止まるまでが長くなりすぎないようにする

## 影響・今後の課題

- 止めるのが、シェルが終わるまでの時間（ふつうは数十ミリ秒、最長 1 秒）だけ遅くなる
- タブを閉じると、シェルと前面のコマンドが終わる。これまでは、対話シェルが SIGTERM を無視して残り、Accompany を止めるまで動き続けていた
- 前面のコマンドの子が、別のプロセスグループで動いているとき（前面のコマンドが自分でプロセスグループを作った）は、そのコマンドが子に伝えなければ届かない。ふつうの端末と同じ
- 止まった（Ctrl+Z）ジョブには SIGCONT を送らない。bash と zsh は SIGHUP を受けると、止まったジョブに SIGHUP と SIGCONT を送る

## 含めないもの

- SIGHUP で終わらないものを SIGKILL で止めること
- Accompany が SIGKILL で止められたとき（合図を受けられないので、PTY が閉じたときのカーネルの SIGHUP に任せる）
