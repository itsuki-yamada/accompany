# 1 行の高さが変わったら、スクロールバックのスクロール位置を合わせ直す

- 日付: 2026-10-22
- ストーリー: #115

## 背景

「長く使っていたらターミナルをスクロールできなくなった」（v0.10.0）という報告があった。原因は分かっていなかったので、Issue に挙げた見当を、長く使ったときの操作を短時間でまとめて行う Playwright のスクリプトで 1 つずつ試した。「スクロール」は、xterm の中のスクロール（スクロールバック）と、ペインの枠のスクロール（はみ出し、#103）の両方を見た。

再現したのは次の 1 つだけ。

- ホイールでスクロールしたことのあるターミナルで、1 行の高さ（フォントの大きさ）が変わると、次のホイールで何十行〜何百行も飛ぶ。上に回しても下に回しても飛び、一番下（最新の行）にも戻れない
- フォントの大きさは、表示の設定で変えたときのほか、「画面に収める（縮小）」では端末の大きさや自分の表示領域が変わるたびに変わる（参加者の出入り、ウィンドウの大きさの変更など）。長く使うほど起きやすい
- 原因は xterm（6.0.0）のスクロールバックの実装。スクロール位置をピクセルで持ち、1 行の高さが変わっても変わる前の高さのピクセルのまま残す。表示している行（`ydisp`）とずれたまま、次のホイールでピクセルを新しい高さで行に直すので飛ぶ。直前にホイールで動かした行を覚えていて（`_latestYDisp`）、表示している行と同じなら同期のときにスクロール位置を設定し直さないため、一度もホイールを使っていないターミナルでは起きない。6.1.0 の beta でも直っていない

再現しなかったもの（試した手順と結果）:

- スクロールバックが上限（1000 行）に達したあと（数千行の出力を何度も、ページの開き直しを含む）。押し出しの数え方（#101、`trimmed-lines.ts`）も含めて、スクロールは普通にできた
- 上にスクロールしている間に出力が続く。読んでいる位置は保たれ、一番下に戻れた
- ペアプロモード（#102）の開始・追従中の出力・終了を、追従する側とされる側の両方で。自分のスクロールは打ち消されなかった
- 端末の大きさの変更（自分のウィンドウ、小さい参加者の参加）、分割と閉じる、Workspace の切り替え、ブラウザのタブを裏にしている間の出力、画面の拡大率（devicePixelRatio）の変更
- 枠からはみ出しているとき（#103、#120）。xterm のスクロールバックはホイールで動き、xterm が一番下のときは枠もホイールで動いた
- マウスの報告モードや代替画面を残したまま終わったアプリ。ホイールはアプリ（シェル）に送られる（報告の文字列やカーソルキーになる）が、これは ESC [?1000h などを受け取った端末として正しい動きで、xterm.js やほかの端末と同じ。報告モードを戻せばスクロールできる。「ターミナルのリセット」でも戻せる

## 決定

- `Pane` で、描くたび（`onRender`）に 1 行の高さを見て、前と変わっていたら、xterm のスクロールバックのスクロール位置を、今表示している行に合わせ直させる
- 合わせ直しは xterm の内部の API で行う。覚えている直前の行（`_viewport._latestYDisp`）を忘れさせてから同期を頼む（`_viewport.queueSync()`）と、同期のときに今表示している行の位置（行 × 新しい高さ）にスクロールする

## 理由

- 1 行の高さはフォントの大きさの設定、縮小表示、描いたあとの測り直し（#103 の `remeasure`）など、いくつもの経路で変わる。フォントの大きさを変える箇所（`setFontSize`）だけで直すと、ほかの経路の分が残る。描いたあとなら、どの経路でも新しい高さが決まっている
- 公開の API（`scrollToLine` など）は、ずれたピクセルからの相対で動くので、合わせ直しに使えない。xterm の内部の API はすでにスクロールバーの高さの計算し直しに使っており（`setFontSize`）、同じ `_viewport` の範囲にとどめる

## 影響

- 上にスクロールして読んでいる途中でフォントの大きさが変わっても、同じ行のあたりを見たまま、続けてホイールで動かせる

## 含めないもの

- マウスの報告モードや代替画面を残して終わったアプリのあと、Accompany が自分でモードを戻すこと（端末として正しい動きを変えることになる。必要なら別のストーリーにする）
- xterm への報告や、xterm の版を上げること
