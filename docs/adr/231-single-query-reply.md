# 端末への問い合わせには、サーバー側の画面だけが答える

- 日付: 2026-11-04
- ストーリー: #231

## 背景

アプリは端末に問い合わせ（デバイス属性・カーソルの位置・色など）を出し、端末が入力として返す返事を読む。git の delta は背景色（OSC 11）とデバイス属性（DA1）を、less や vim なども起動時にいくつか問い合わせる。

これまでは、参加者のブラウザの xterm.js がそれぞれ返事を作り、人の入力と同じ `onData` に乗せてサーバーに送っていた。2 人以上がつながっていると、PTY には返事が人数分届き、2 つ目以降はアプリへの入力として読まれる。#227 の調査で、`git add -p`（delta を使う設定）の問い合わせの行に `^[]11;rgb:0000/0000/0000^[\^[[?1;2c` が入って答えがはじかれる、less が余分な文字をコマンドとして読んで抜けられなくなる、を確かめた。1 人では起きない。

一方、サーバーは途中参加者に画面を復元するために、PTY の出力をすべて `@xterm/headless` の画面にも書いている（`TerminalSession`）。この画面も xterm.js と同じパーサーで問い合わせを読み、`onData` に返事を出すが、これまでは読み捨てていた。

## 検討した選択肢

### 誰が答えるか

1. サーバー側の画面（headless）だけが答え、返事を PTY に書く。ブラウザには答えさせない
2. ブラウザのうち 1 人（最後に入力した人、最初に参加した人など）の返事だけを通す
3. サーバーで、短い時間に届いた同じ返事を 1 つにまとめる

### ブラウザで返事を止める方法

xterm.js 6.0.0 では、問い合わせへの返事も人の入力も `coreService.triggerDataEvent` から `onData` に出る。

- A. `triggerDataEvent` の `wasUserInput` で見分ける。返事は `false`、キー入力・貼り付け・マウスの報告は `true` で呼ばれる。ただしフォーカスの報告（CSI I / CSI O）も `false` で、公開されていない内部（`_core.coreService`）に手を入れる必要がある
- B. `onData` に届いた文字列の形（`ESC [ ? 1 ; 2 c` など）で見分けて捨てる。貼り付けた文字列やキー入力と形で区別しきれない
- C. 公開 API のパーサーのハンドラー（`terminal.parser.registerCsiHandler` など）で問い合わせのシーケンスを先に受け止め、`true` を返して xterm.js の既定の処理（返事を作る）まで行かせない

## 決定

- 選択肢 1 と C。端末への問い合わせには、サーバー側の画面だけが答え、その返事を PTY に 1 回だけ書く。参加者の数、誰が入力したかに関係なく 1 回。参加者が 0 人（誰も開いていない間に動いているコマンド）のときも答える
- サーバーの返事は、人の入力ではないので `TerminalSession.write` を通さず、PTY に直接書く（入力の時刻、エージェントの判定には数えない）
- ブラウザでは、`Pane` を作るときに `ignoreQueries`（`app/server/src/terminal-queries.ts`）で、下の表の「ブラウザ」の列の問い合わせをパーサーのハンドラーで受け止める。`onData` はこれまでどおりすべてサーバーに送る。キー入力・貼り付け（ブラケットペースト）・マウスの報告・フォーカスの報告は、人の操作なので止めない
- 色の OSC に、色の設定と問い合わせが混ざっているとき（`OSC 10 ; rgb:.. ; ?` など）は、ブラウザでは問い合わせの部分だけを除いた OSC を書き直して、色の設定は反映する

### 対象の問い合わせ

xterm.js 6.0.0 の `triggerDataEvent` の呼び出しと、よく使われる問い合わせを洗い出した。

| 問い合わせ | シーケンス | これまで答えていたもの | これから答えるもの |
|---|---|---|---|
| DA1（デバイス属性） | `CSI c` | ブラウザ（人数分） | サーバー（headless が `CSI ? 1 ; 2 c`） |
| DA2 | `CSI > c` | ブラウザ（人数分） | サーバー（headless が `CSI > 0 ; 276 ; 0 c`） |
| DSR（状態） | `CSI 5 n` | ブラウザ（人数分） | サーバー（headless が `CSI 0 n`） |
| DSR / CPR（カーソルの位置） | `CSI 6 n`、`CSI ? 6 n` | ブラウザ（人数分） | サーバー（headless が自分の画面のカーソルの位置で答える。端末の大きさは参加者と同じ） |
| DECRQM（モードの問い合わせ） | `CSI Ps $ p`、`CSI ? Ps $ p` | ブラウザ（人数分） | サーバー（headless が自分の画面のモードで答える） |
| DECRQSS（設定の問い合わせ） | `DCS $ q Pt ST` | ブラウザ（人数分） | サーバー（headless） |
| 文字色・背景色・カーソルの色 | `OSC 10/11/12 ; ?` | ブラウザ（人数分。それぞれの配色の色） | サーバー（既定の配色の色。下を参照） |
| 256 色の番号ごとの色 | `OSC 4 ; n ; ?` | ブラウザ（人数分） | サーバー（xterm.js の既定の 256 色） |
| ウィンドウ・文字の大きさ（ピクセル、文字数） | `CSI 14 t`、`CSI 16 t`、`CSI 18 t` | 誰も答えない（xterm.js の `windowOptions` が既定で無効） | 誰も答えない（変えない） |
| XTVERSION、DA3、XTGETTCAP、kitty のキーボードの問い合わせなど | `CSI > q`、`CSI = c`、`DCS + q`、`CSI ? u` | 誰も答えない（xterm.js が実装していない） | 誰も答えない（変えない） |
| フォーカスの報告 | `CSI I`、`CSI O`（問い合わせではなく報告） | ブラウザ | ブラウザ（変えない） |

### 色の問い合わせに返す色

`@xterm/headless` は色を持たず、OSC 4/10/11/12 の問い合わせには答えない（返事を作るのはブラウザ側の `CoreBrowserTerminal` だけ）。そこでサーバーで、OSC 4/10/11/12 のハンドラーを登録して答える。

- 文字色（OSC 10）: `#cccccc`（`rgb:cccc/cccc/cccc`）
- 背景色（OSC 11）: `#000000`（`rgb:0000/0000/0000`）
- カーソルの色（OSC 12）: `#ffffff`（`rgb:ffff/ffff/ffff`）
- 256 色（OSC 4）: xterm.js の既定の 256 色（`DEFAULT_ANSI_COLORS` と同じ）

これはブラウザの既定の配色（暗い。docs/adr/36-appearance.md）と同じ色で、参加者の配色の設定によらない。色は `terminal-queries.ts` の `defaultColors` に置き、ブラウザの暗い配色もこれを使う。返事の形は xterm.js と同じ（16 ビットの `rgb:rrrr/gggg/bbbb`、ST で終わる）。

## 理由

- 選択肢 1: サーバー側の画面は PTY の出力をすべて同じ順番で読んでいて、端末の大きさも参加者と同じなので、カーソルの位置・モードの返事をブラウザと同じに作れる。参加者の数やつながり方（途中参加、切断）に左右されず、誰も見ていない間も答えられる
- 選択肢 2 は、選ばれた人が切断した・タブを閉じた直後などに返事が 0 回や 2 回になりうる。だれを選ぶかの状態をサーバーとブラウザで合わせる仕組みも要る。選択肢 3 は、まとめる時間の決め方に依存し、同じ問い合わせが続けて出た場合と区別できない
- C: 公開 API だけで、問い合わせのシーケンスそのものを見て止められる。A は内部に依存するうえ、フォーカスの報告を見分けられない。B は貼り付けやキー入力と区別しきれない
- 色を参加者ごとにしない: 返事は 1 つしか送れないので、だれかの配色に決める必要がある。既定の配色にしておけば、参加者の数や設定によらず同じ色になる。暗い配色が既定で、多くの参加者の配色と合う

## 影響・今後の課題

- 明るい・見やすさ重視の配色を選んだ参加者がいても、色の問い合わせには暗い配色の色で答える。delta などは背景が暗い前提の色で表示するので、明るい配色の人には見にくいことがある。参加者ごとに色を変えられない以上、共有の配色を決める（たとえばホストの配色を使う）ことを検討する
- アプリが OSC 10/11/12/4 で色を設定しても、サーバーは色を覚えないので、その後の問い合わせには既定の色で答える（ブラウザはこれまでどおり設定した色で表示する）
- 返事は headless が出力を読み終えたときに書くので、これまで（ブラウザが受け取って返事をサーバーに送る）より速く届く
- 今後 xterm.js を上げて、ブラウザ側で新しい問い合わせに答えるようになったら（XTVERSION など）、`ignoreQueries` にも加える。headless も同じパーサーなので、サーバーは自然に答える
