# 端末の大きさは一番大きい表示領域（フル HD まで）に合わせ、小さい画面ではスクロールか縮小で見る

- 日付: 2026-10-16
- ストーリー: #51

## 背景

これまで端末（PTY）の大きさは、参加者のうち一番小さい表示領域に合わせていた（#5）。この方法では、画面の小さい人やフォントを大きくした人（#36）が 1 人参加するだけで、全員の端末が小さくなる。

1 つのコマンドの画面は 1 つの大きさでしか描けない（TUI は列・行の位置を指定して描く）ので、参加者ごとにレイアウトを変えることはできない。そこで、大きさの基準と見せ方を変える。基準の方針はユーザーと相談して次のように決めた（Issue #51 の本文）。

- 端末の大きさは、参加者のうち一番大きい表示領域に合わせる
- ただし各参加者の表示領域は最大 1920×1080 ピクセル（フル HD）とみなし、各自のフォントの大きさで列数・行数に直す
- それより表示領域の小さい参加者は、文字の大きさはそのままで、はみ出した部分をスクロールして見る。「画面に収める（縮小）」にも切り替えられる
- 描き直しが起きるのは、「一番大きい表示領域」が変わったときだけ

このほかに、次のことを決める必要があった。

- フル HD の上限をどこで掛けるか
- スクロールをどう実装するか（マウスの位置がずれないこと）
- 縮小をどう実装するか（同上）
- 「画面に収める」の設定を、誰の単位で、どこに持つか

## 検討した選択肢

### フル HD の上限をどこで掛けるか

1. ブラウザで、表示領域の幅・高さを 1920×1080 までに切り詰めてから、自分のフォントの大きさで列数・行数に直してサーバーに送る
2. サーバーで、列数・行数に上限を掛ける

### スクロールの実装

1. xterm の要素を端末の大きさのまま置き、ペインのターミナルの領域（`.pane-terminal`）を `overflow: auto` にして、ブラウザのスクロールで見せる
2. xterm の要素を CSS の `transform: translate` でずらし、スクロールを自前で作る

### 縮小の実装

1. CSS の `transform: scale` や `zoom` で縮める
2. xterm のフォントの大きさを、端末全体が収まるところまで小さくして描く

### 「画面に収める」の設定の持ち方

1. 参加者ごとに 1 つ持ち、表示の設定（#36）と一緒にブラウザ（localStorage）に保存する
2. ペインごとに切り替えるボタンをペインのバーに置く
3. 保存しない

## 決定

- 上限: 選択肢 1。ブラウザが、ターミナルの領域の大きさ（スクロールバーを含む `offsetWidth` / `offsetHeight`）を 1920×1080 までに切り詰め、設定したフォントの大きさでの 1 文字の幅・高さで割って、列数・行数をサーバーに送る。サーバー（`TerminalSession.fitToLargest`）は、参加者から届いた列数・行数のそれぞれ一番大きいものを端末の大きさにする
- スクロール: 選択肢 1。`.pane-terminal` を `overflow: auto` にし、xterm の要素（`.xterm`）を `width: max-content` で端末の大きさに合わせる。xterm のスクロールバック用のスクロールバーが文字に重ならないよう、`.xterm-screen` の右に 14px をあける。検索でヒットを選んだときは、ヒットが見えていなければ表示領域の中央に来るようにスクロールする
- 縮小: 選択肢 2。「画面に収める（縮小）」のときは、端末全体が表示領域に収まる倍率を求めてフォントを小さくし（0.5px 刻み、下限 2px）、はみ出していればさらに 0.5px ずつ小さくする。サーバーに伝える大きさは、縮小する前のフォント（設定した大きさ）で測った 1 文字の大きさで計算する。xterm（6.0）はフォントの大きさを変えただけでは、スクロールバックのスクロールバーの高さと入力欄（カーソルの位置に置く `textarea`）の位置を計算し直さず、前の大きさのまま端末の外にはみ出して、表示領域のスクロールできる範囲が残る。そこで、フォントを変えたらスクロールバーを計算し直させ（内部の `_viewport.queueSync()`）、`.xterm` を `overflow: hidden` にして端末の外を切る
- 設定: 選択肢 1。表示の設定に「端末が画面より大きいとき」（スクロールして見る / 画面に収める（縮小））を足し、`accompany.appearance` に `overflow: "scroll" | "fit"` として保存する。既定はスクロール。読めない値は既定にする
- 1 文字の大きさは、`@xterm/addon-fit` と同じく xterm の内部の値（`_core._renderService.dimensions.css.cell`）から読む。表示領域の計算を自前で行うので、`@xterm/addon-fit` は使わなくなり、依存から外す

## 理由

- 上限をブラウザで掛ける: フォントの大きさは参加者ごとに違い、同じフル HD でも収まる列数・行数は人によって違う。サーバーは各参加者のフォントの大きさを知らないので、ピクセルで上限を決めて文字の大きさで換算するのはブラウザでしかできない。スクロールバーを含む大きさを使うのは、はみ出してスクロールバーが出たときに表示領域が狭く計算され、伝える大きさが揺れるのを防ぐため
- スクロールをブラウザのスクロールにする: xterm はマウスの位置から文字の位置を、`.xterm-screen` の `getBoundingClientRect()` と `clientX` / `clientY` の差を 1 文字の大きさで割って求める。ブラウザのスクロールでは要素の位置（`getBoundingClientRect()`）がそのまま動くので、選択・URL のクリック・右クリック・TUI へのマウスの報告がずれない。`translate` でずらす方法も位置は合うが、スクロールバーやホイールを自前で作る必要があり、シンプルさに欠ける
- ホイール: xterm（6.0）のスクロールバックは、スクロールできたときだけホイールのイベントを消費する。そのため、スクロールバックの端に達したホイールや横方向のホイールは、ブラウザが `.pane-terminal` のスクロールに回す。追加の処理はしない
- 縮小をフォントの大きさで行う: `transform: scale` や `zoom` では、`getBoundingClientRect()` は縮んだ大きさを返すのに、xterm が割る 1 文字の大きさは縮める前のままなので、マウスの位置と文字の位置がずれる（選択・URL のクリックが別の文字に当たる）。フォントの大きさで縮めれば、xterm にとっては普通の小さい文字の端末なので、ずれが起きない。フォントの大きさを変えると描き直しが起きるが、縮小し直すのは端末の大きさか自分の表示領域が変わったときだけなので、頻度は低い
- 縮小前の大きさで伝える: 縮小した文字の大きさで伝えると、本来より大きい表示領域を持っているように見え、端末が大きいまま戻らなくなる（縮小 → 大きく伝える → さらに縮小、の循環）。設定したフォントの大きさを基準にすれば、縮小しても端末の大きさは変わらない
- 設定を参加者ごとにブラウザに保存: 見せ方は「どう見えるか」の設定で、#36 の配色・フォントの大きさと同じ性質を持つ（docs/adr/36-appearance.md）。ペインごとのボタンは UI が増え、ストーリーの完了条件には不要。必要になれば足す

## 影響・今後の課題

- 画面の小さい人は、端末の右下（シェルのプロンプトがあることが多い下の行など）を見るためにスクロールが要る。入力すると、ブラウザが入力欄（カーソルの位置）を見える位置に動かすことがあるが、カーソルを追いかける処理はしていない。必要になれば足す
- スクロールバックのある端末でホイールを上に回すと、まずスクロールバックが戻り、`.pane-terminal` の縦のスクロールはスクロールバックの先頭に達してから動く。ペインのスクロールバーでも動かせる
- マウスの報告モードを有効にした TUI では、ホイールは TUI に送られ、`.pane-terminal` はホイールではスクロールしない（スクロールバーで動かす）
- フル HD の上限はブラウザで掛けるが、サーバーでも端末の大きさを **512 列・256 行** までに切り詰める（`terminal.ts` の `maxSize`。範囲外の値は捨てずに上限に丸める）。基準が「一番大きい」になったので、1 人から大きすぎる値が届くと、全員の端末・サーバー側の画面（@xterm/headless）・PTY がその大きさになる（1000×1000 なら 1 端末で約 24MB、ブラウザの DOM で 100 万セル、#34 の保存のたびの書き出しも重くなる）。待ち受けは loopback だけで参加者は信頼できる前提（#7 の認証の前）でも、改造したブラウザだけでなく、フォントの読み込み前に 1 文字の幅を小さく測るなどの不具合でも起きうるので、備えとして入れる。512×256 は、フル HD を最小のフォント（8px）で埋めた大きさ（およそ 400 列・100 行）より大きく、ふつうの使い方では届かない。#34 の復元で保存した大きさを読むときも、同じ値で切り詰める
- 列数と行数は、それぞれ別々に一番大きいものを取る。そのため、横長の画面の人と縦長の画面の人がいると、端末は誰の画面よりも大きくなり（列数は横長の人、行数は縦長の人に合わせる）、全員がどこかをスクロールして見ることになる
- 1 文字の大きさとスクロールバーの再計算に xterm の内部の API を使うので、`@xterm/xterm` は E2E を通した 6.0.0 に固定する（tarball から入れる利用者の環境に、確かめていない 6.x が入らないように）
- 一番大きい表示領域の人がウィンドウを小さくしたり抜けたりすると、ほかの全員の端末も小さくなる（描き直しが起きる）。これは #5 のときと同じ性質
- docs/adr/36-appearance.md の「端末の大きさは参加者のうち一番小さいものに決める」は、この ADR で置き換える
