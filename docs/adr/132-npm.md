# npm に、起動役の accompany と OS・CPU ごとの実行ファイルのパッケージを公開する

- 日付: 2026-10-22
- ストーリー: #132

## 背景

`npx accompany` で、Bun を入れずに起動できるようにする。npm のパッケージ名は `accompany`、OS と CPU ごとの実行ファイルは `@itsuki-yamada/accompany-<OS>-<CPU>` にする（ユーザーの判断）。次のことを決める必要があった。

- パッケージの分け方と、実行ファイルの選び方
- 起動の仕組み（引数、標準入出力、止める合図、終了コード）と、Node の版の下限
- 公開のきっかけと認証
- 公開する前の確かめ方

## 検討した選択肢

### パッケージの分け方

1. 主パッケージ `accompany` と、OS と CPU ごとのパッケージ 4 つ。主パッケージの optionalDependencies に 4 つを書き、それぞれの `os` と `cpu` で、入れたマシンに合うものだけが入るようにする（esbuild などと同じ）
2. 主パッケージの postinstall で、Release から合う実行ファイルをダウンロードする
3. 4 つの実行ファイルを 1 つのパッケージに入れる

### 起動の仕組み

1. 主パッケージの bin を Node の小さな起動役にし、合うパッケージの実行ファイルを子プロセスとして起動する
2. postinstall で、bin を実行ファイルそのものに置き換える

### 認証

1. npm の Trusted Publishing（GitHub Actions の OIDC）
2. npm のアクセストークンを Actions のシークレットに置く

### 公開する前の確かめ方

1. 公開するパッケージを npm pack し、別のディレクトリに入れて、npx で起動できることだけを確かめる
2. 1 に加え、入れたものに対して E2E を全件流す

## 決定

- 分け方は 1 にする
  - `@itsuki-yamada/accompany-<OS>-<CPU>`（darwin-arm64・darwin-x64・linux-x64・linux-arm64）は、実行ファイルを `bin/accompany` に入れ、`os` と `cpu` を指定する。Linux 向けは `libc: ["glibc"]` も指定する（musl では動かないため。知らない npm は無視する）
  - 主パッケージ `accompany` は、4 つを同じ版の optionalDependencies にする
  - 主パッケージの元は `npm/accompany/`（起動役、README、package.json のひな形）に置き、版と optionalDependencies は `.github/scripts/build-npm-packages.sh` が `app/server/package.json` の版で書き込む。OS と CPU ごとのパッケージの package.json も同じスクリプトが作る
- 起動の仕組みは 1 にする。`npm/accompany/bin/accompany.js` は、`process.platform` と `process.arch` から合うパッケージの実行ファイルを `require.resolve` で探し、引数をそのまま渡して `stdio: "inherit"` で起動する
  - 止める合図: SIGINT・SIGTERM・SIGHUP を受けたら実行ファイルに伝え、実行ファイルが保存して終わるのを待つ。端末の Ctrl+C はプロセスグループ全体に届くので、実行ファイルには二度届くが、実行ファイルは二度目以降を無視する（bunx と同じ）
  - 終了コード: 実行ファイルの終了コードで終わる。合図で終わったときは、起動役も同じ合図で終わる
  - 対応していない OS と CPU や、合うパッケージが入っていない（`--omit=optional` など）ときは、理由を表示して終了コード 1 で終わる
- Node の版の下限は 18 にする（`engines`）。起動役は CommonJS と古くからある API だけを使う。手元で Node 18.20（npm 10.8）で、入れて起動して止められることを確かめた
- 公開は `release.yml` の `npm` ジョブにする。`release`（Release を作るジョブ）のあとに、同じ実行ファイル（成果物 `accompany-binaries`）からパッケージを作り、`check-npm.sh` で起動を確かめてから、`publish-npm.sh` で OS と CPU ごとのパッケージ → 主パッケージの順に公開する。既に公開した版は飛ばすので、版を上げたときだけ公開される。edge は公開しない。公開のステップは、リポジトリ変数 `NPM_PUBLISH` が `true` のときだけ流す（パッケージを作って確かめるところは、変数によらず流す）
- 認証は 1 にする。`npm` ジョブだけに `id-token: write` を渡す。Trusted Publishing には npm 11.5.1 以上が要るので、`actions/setup-node` で Node 24 を使う。トークンは作らない
- dry-run（`workflow_dispatch`）でも、パッケージを作って起動を確かめ、`npm publish --dry-run` で何を公開するかを表示する
- 確かめ方は 2 にする。`e2e.yml` の matrix に `npm` を足し、4 つの実行ファイルとパッケージを作り、`check-npm.sh` で主パッケージと linux-x64 のパッケージを別のディレクトリに入れて、`npx accompany --port <ポート>` で起動して画面が返ること、Ctrl+C と同じくプロセスグループに SIGINT を送って止まることを確かめる。そのあと、`ACCOMPANY_CMD` を入れた起動役（`node_modules/.bin/accompany`。`npm i -g accompany` で入るものと同じ）にして E2E を全件流す
  - E2E の起動コマンドを npx にしなかったのは、npx（npm）だけに合図を送る E2E（下の `launch.spec.ts`）が Linux で通らないため。npm は bin を `sh -c` で起動し、Linux の sh（dash）は自分を置き換えずに待つので、npm が伝えた合図がシェルで止まり、起動役に届かない（macOS の sh は置き換えるので届く）。npm とシェルの振る舞いで、起動役では直せない。端末の Ctrl+C はプロセスグループ全体に届くので、npx でも止まる（`check-npm.sh` で確かめる）
  - npx が SIGINT で終わるときの終了コードは、npm の版によって 0 か 130 になる。どちらも止まったものとする
- E2E に `launch.spec.ts` を足す。起動の引数が誤っているときに終了コード 1 で終わること、起動したプロセス（npm の起動役など）だけに SIGINT / SIGTERM を送っても、保存してから止まり、起動し直すと戻ることを、すべての起動のしかたで確かめる

## 理由

- postinstall（2）は、`--ignore-scripts` を使う環境やプロキシの内側で失敗し、GitHub へのダウンロードも要る。optionalDependencies なら npm のレジストリだけで済み、入れたマシンに合う 1 つだけを落とす
- 1 つのパッケージに 4 つ（3）は 300MB を超え、使わないものまで落とす
- 起動役を挟むと Node のプロセスが 1 つ増えるが、npx で起動したとき、bin の置き換え（2）は postinstall に頼ることになる。起動役なら、引数・入出力・合図・終了コードを素直に渡せる
- Trusted Publishing なら、漏れたり期限が切れたりするトークンを持たずに済み、公開したパッケージに来歴（provenance）が付く
- 起動役は、引数と合図を渡しそこねると E2E のすべてに関わる。リポジトリは PUBLIC で、ランナーの費用はかからず、matrix なので待ち時間もほとんど増えない。E2E を全件流せば、引数（`--port`・`--fresh`・`--min-window`・`-- <command>`）とプロセスグループへの合図も、実行ファイルを直接起動したときと同じ確かめ方になる。npx が引数をそのまま渡すことは、`check-npm.sh` の `--port` と、手元で `-- claude --resume` が渡ることで確かめた

## 影響・今後の課題

- プルリクの E2E のチェックに `e2e (npm)` が増える（必須のチェックにするかは持ち主が決める）
- 正式な Release を作ったあとに npm へ公開するので、Release はあるが npm にはまだない、という時間が少しある。`npm` ジョブが落ちたとき（Trusted Publishing の設定がない、など）も、Release はそのまま残る。直したあとは、実行ファイルの成果物が残っている 1 日のうちに `release.yml` の失敗したジョブを再実行すれば、公開していないものだけが公開される
- 最初の公開（パッケージを作る）と、Trusted Publishing の設定は、持ち主が npm 側で行う（プルリクの本文に手順を書く）。終えたら、リポジトリ変数 `NPM_PUBLISH` を `true` にする。それまでは公開のステップを飛ばすので、`npm` ジョブは落ちず、Release のワークフローも赤にならない
- npx だけに（プロセスグループでなく）合図を送ったとき、Linux では Accompany に届かない（npm と sh の振る舞い）。kill などで止めるときは、プロセスグループに送るか、`npm i -g` で入れた `accompany` を使う
- Windows と musl には対応しない
