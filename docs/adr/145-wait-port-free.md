# E2E で Accompany を止めるときは、ポートが空くまで待つ

- 日付: 2026-10-23
- ストーリー: #145

## 背景

手元（macOS）で E2E を全件流すと、ときどき起動の時点で「Failed to start server. Is port … in use?」（EADDRINUSE）になって数件落ちていた。流し直すと通り、CI（ubuntu）では起きていない。

`e2e/tests/accompany.ts` の `stop` は、プロセスグループ全体に signal を送り、`kill(-pgid, 0)` が失敗する（グループにプロセスがいなくなる）まで待ってから戻る。次のテストは、E2E_PORT_BASE からの決まったずれ（offset）の同じポートで起動する。

## 分かったこと

- 全件を `--repeat-each 2` で流すと（E2E_PORT_BASE=9701、workers 1）、2 回とも `agent-status.spec.ts` の「シェルから起動したエージェントを見分けて…」（とその次のテスト）が EADDRINUSE で落ちた。どちらも、直前のテストは「矢印キーやファンクションキーだけでは…」（画面を描き続ける TUI を動かす）だった。`agent-status.spec.ts` だけを `--repeat-each 4` で流したときは落ちなかった
- 起動に失敗したときに記録したもの（一時的に `startAccompany` に足した）
  - `lsof -nP -i :9701` には何も出ない。Accompany や偽のエージェントのプロセスも `ps` の一覧の名前では出ない
  - `netstat -anv -p tcp` では、`127.0.0.1.9701` を `LISTEN` しているソケットがあり、持ち主は `bun:51483` だった。ほかは TIME_WAIT だけ
  - `ps` では、51483 は前のテストの Accompany（親はテストのワーカー、自分のプロセスグループ）で、状態は `?Es`（終了している途中）だった。その PTY のコマンド（51487）も `?Es` だった
  - 同じポートで待ち受けられるか 0.1 秒ごとに試すと、0.5 秒ほどで待ち受けられるようになった
- つまり、前のテストの Accompany は終了している途中で、まだポートで待ち受けている。終了している途中のプロセスは `kill(-pgid, 0)` では見つからない（`lsof` にも出ない）ので、`stop` はグループが終わったとみなして戻り、次のテストが同じポートで起動して失敗していた。TIME_WAIT は原因ではない（サーバー側から閉じた接続の TIME_WAIT が残っていても、Bun で同じポートで待ち受けられることを確かめた）
- 終了に時間がかかるのは、PTY のコマンドが出力を続けている間に止めたときと思われる（PTY を閉じるときに、読まれていない出力を待つ）。ただし、同じ形で止めて起動し直すことを 20 回繰り返しても再現せず、どの条件で長引くかまでは特定していない

## 検討した選択肢

- A. `stop` で、プロセスグループが終わったあとに、同じアドレスとポートで待ち受けられるようになるまで待つ
- B. 起動するポートを 0 にして OS に選ばせ、起動の出力（`Accompany: http://127.0.0.1:<port>`）から読む
- C. 起動が EADDRINUSE で失敗したら、少し待って起動し直す
- D. `stop` で、起動したコマンドのプロセスが終わった（Node の `exit` が届いた）ことも待つ

## 決定

A を採る。`stop` は、プロセスグループが終わったあと、Accompany が表示した URL のアドレスとポートで待ち受けられるようになるまで 20 ミリ秒ごとに確かめて待つ。10 秒たっても空かないときは、そのことを例外にして、テストを落とす。

## 理由

- A は、`stop` がすでに約束していること（次のテストが同じポートで起動できるまで待つ）を、そのまま確かめる。起動のしかたを差し替えたとき（ACCOMPANY_CMD で npm や bunx の起動役が間に入るとき）も、待ち受けているのがどのプロセスかによらず効く
- B は、ぶつかることそのものがなくなるが、`--port` を確かめるテストや、起動に失敗するテストは決まったポートを使い続けるので、E2E_PORT_BASE の仕組みと、ポートを決める方法が 2 つになる。また、テストごとにページの origin が変わる。原因が分かったので、今の仕組みのままで直せる
- C は、`terminal.spec.ts` の「同じポートで Accompany が動いているときは、起動に失敗する」とぶつかり、ほかの原因で使われているときも隠してしまう
- D は、既定の起動（`exec` で Accompany 自身が起動したプロセスになる）では効くが、起動役が間に入るときは、待ち受けている孫のプロセスの終わりを待てない

## 影響

- E2E_PORT_BASE で複数の作業ツリーから同時に流す仕組みは変えない
- `stop` は、ポートが空くまでの分（ふつうは 0、長引いたときで 1 秒未満）だけ長くかかる
- 止めたあともポートがほかのプロセスに使われているときは、次のテストの起動ではなく `stop` で、ポートが空かないことが分かる

## このストーリーに含めないもの

- 終了が長引く条件（PTY を閉じるときの待ち）の特定と、Accompany 本体の止め方を変えること。待ち受けをやめてから PTY のコマンドを止めるなどは、使う人には違いが見えないので、困ったときに考える
- E2E を並行に流すこと
