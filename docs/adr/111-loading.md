# ゲストが開いたときの初動を速くし、読み込み中であることを表示する

- 日付: 2026-10-22
- ストーリー: #111

## 背景

ゲストとして URL を開いて入ったときの最初の表示が重く、その間に何も出ないので、動いているのか分からなかった。ゲストは Live Share のサーバーの共有や SSH のポート転送など、ホストとは別のマシンからネットワーク越しに開くことが多い。

### 計測

開いてから使えるようになるまでを、段階ごとに測った。

- 遅延と帯域は、ブラウザと Accompany の間に TCP の中継を挟んでかけた（片道 RTT/2 の遅延と、向きごとの帯域。HTTP と WebSocket の両方にかかる）。条件は、制限なし、RTT 100ms / 10Mbps、RTT 200ms / 2Mbps
- ホストが長く使っていた状態として、1 つの Workspace に 1 または 4 つのターミナルを置き、それぞれ色付きの 1,100 行を出してスクロールバックを溜めた（1 行 100 文字ほど）
- 起動は、ソースから（`bun app/server/src/cli.ts`）、tarball から（`bunx --package <tarball> accompany`）、実行ファイル（`bun build --compile`、darwin-arm64）の 3 通り
- 時刻は、ページを開き始めてからのミリ秒（Chromium、1280×800、キャッシュなし）。「使える」は、表示中のすべてのターミナルに画面が描かれた（変更後は、読み込み中の表示が消えた）とき

変更前（v0.13.0）の主な結果（RTT 200ms / 2Mbps、ターミナル 4 つ）:

| 段階 | ソース | tarball | 実行ファイル |
|---|---|---|---|
| HTML が届く | 221 | 220 | 208 |
| JS・CSS が届く | 2185 | 2176 | 2704 |
| Workspace の配置が届く | 2427 | 2394 | 2935 |
| ターミナルの WebSocket がつながる（最後の 1 つ） | 3300 | 3260 | 3816 |
| ターミナルの最初の画面が届く（最後の 1 つ） | 3851 | 3808 | 4366 |
| 使える | 3878 | 3841 | 4396 |
| 受信量 | 972KB | 972KB | 1107KB |

分かったこと:

- 一番大きいのは画面の JS（436KB）。Bun の HTML の取り込みは本番では縮める（minify）が、圧縮（gzip など）はしないので、そのまま送っていた。実行ファイルでは縮めもしておらず 571KB だった。キャッシュの効く 2 回目は速い（ソース・tarball はハッシュ付きの名前で immutable。実行ファイルは Cache-Control がなく、毎回問い合わせていた）
- 次が、途中から開いたときに送るターミナルの画面（スクロールバックを含む）。1,000 行で 1 ターミナル 135KB ほどあり、これも圧縮せずに送っていた
- ターミナルの WebSocket は、ブラウザが同じホストへの接続を 1 つずつしか始めない（RFC 6455）ため、ターミナルの数だけ RTT がかかる（4 つで RTT 4 回分ほど）
- 段階の順序は、HTML → JS・CSS → Workspace の WebSocket → 配置 → ターミナルの WebSocket → 画面。Workspace の WebSocket は JS が動いてからつなぐ
- サーバーの起動（URL を表示するまで）は、ソース・tarball とも 20ms ほど（tarball を初めて bunx で開くときだけ、展開で 400ms ほど）。実行ファイルを初めて動かすときは macOS の確認で 800ms ほど。どれも初動の遅さの原因ではなかった
- エージェントの判定（ps）は、参加したときに配るのは判定済みの結果なので、初動を待たせていない

## 決定

### 速くする

- 画面のファイル（HTML・JS・CSS）を gzip で圧縮して配る。Bun の HTML の取り込みが作るファイルは、名前と中身を Bun に任せたまま使いたいので、起動時に一度だけ使い捨てのサーバーで Bun に配らせて取り出し、圧縮して `routes` に置く（`app/server/src/static-assets.ts`）。ブラウザが gzip を受け付けないときは圧縮せずに返す。名前にハッシュの入ったファイルは、Bun が Cache-Control を付けない実行ファイルでもずっとキャッシュさせる
- WebSocket の圧縮（permessage-deflate）を有効にし、1KB 以上のメッセージ（途中から開いた人に送る画面、まとまった出力）は圧縮して送る。打った文字のエコーのような小さいものは圧縮しない
- 実行ファイルを作るときに `--minify` を付け、画面の JS を tarball と同じく縮める。エラーのときに縮めたコードではなく元のソースの行を出すよう、`--sourcemap` も付ける

変更後（RTT 200ms / 2Mbps、ターミナル 4 つ）:

| 段階 | ソース | tarball | 実行ファイル |
|---|---|---|---|
| HTML が届く | 211 | 212 | 211 |
| JS・CSS が届く | 892 | 898 | 891 |
| Workspace の配置が届く | 1114 | 1145 | 1111 |
| ターミナルの WebSocket がつながる（最後の 1 つ） | 1985 | 2043 | 1990 |
| ターミナルの最初の画面が届く（最後の 1 つ） | 2017 | 2064 | 2010 |
| 使える | 2048 | 2085 | 2031 |
| 受信量 | 138KB | 138KB | 138KB |

ほかの条件の結果は、プルリクの本文に載せた。どの起動の方法でも、RTT 200ms / 2Mbps では 3.2〜4.4 秒が 1.4〜2.1 秒に、RTT 100ms / 10Mbps では 1.0〜1.4 秒が 0.6〜0.9 秒になった。サーバーの起動は、圧縮の分だけ 15ms ほど延びる。

### 読み込み中の表示

- HTML に読み込み中の表示（`#loading`、role="status"、名前は「読み込み中」）を最初から置き、JS を読み込む前から出す。画面全体を覆い、組み立て途中の画面は見せない
- Workspace の配置が届き、表示中のターミナルすべての最初の画面を書き終えたら消す。一度消したら、もう出さない（Workspace の切り替えでは出さない）
- ターミナルの画面が空のときは画面を送らないので、サーバーはつないだときの画面を送り終えたことを `restored` で知らせる。ブラウザはそれまでに届いた画面を書き終えてから、読み込みを終えたとみなす

### つながらないとき

- Workspace の WebSocket が切れたら（サーバーが止まった、ネットワークが切れた）、読み込み中の表示を消し、「Accompany との接続が切れました」と「再読み込み」のボタンを画面の上に帯で出す（role="alert"）。切れる前の画面は、そのまま見られる
- 自動ではつなぎ直さない。再読み込みは、そのページを開いている人が行う

## 理由

- 遅い回線では、受信量が初動の時間をほぼ決めていた。JS とターミナルの画面は文字ばかりでよく縮む（JS は 436KB → 117KB、画面は 4 ターミナルで 540KB → 十数 KB）
- 圧縮は、リバースプロキシなど Accompany の外に任せることもできるが、ポート転送や Live Share はそのまま中継するだけなので、Accompany が自分で行う
- 起動時に Bun に配らせて取り出す方法は、ソース・tarball・実行ファイルのどれでも同じように動く。`Bun.build` で自分でバンドルし直す方法は、実行ファイルの中ではソースを読めないため使えない
- 読み込み中の表示を HTML に置くと、JS（圧縮しても 100KB ほど）を待たずに出せる。JS で出すと、一番時間のかかる JS の読み込みの間に何も出ない
- 自動でつなぎ直す（開き直す）と、サーバーを止めている間に開いていたページがすべて参加者として戻り、参加者の一覧や画面の大きさ（一番小さい参加者に合わせる）が知らないうちに変わる。止めたあとに開き直すかは、開いている人が決める

## 影響

- サーバーの起動が、画面のファイルを圧縮する分（15ms ほど）遅くなる
- 1KB 以上の出力は圧縮して送るので、そのぶんサーバーの CPU を使う
- ターミナルの WebSocket に、`restored` のメッセージが増える（古いブラウザは知らない種類として無視する）

## 含めないもの

- ターミナルの WebSocket を 1 本にまとめる（多重化する）こと。ターミナルの数だけかかる RTT（4 つで RTT 4 回分ほど）は、変更後の初動で一番大きい部分だが、プロトコルの作りを変えるので別のストーリーにする
- Workspace の WebSocket を、JS より先に（HTML の中で）つなぐこと
- brotli での圧縮（gzip より 2 割ほど小さいが、起動時の圧縮に 400ms ほどかかる）
- 途中から開いた人に、スクロールバックの全量ではなく見えている部分から先に送ること
- 自動でつなぎ直すこと
