# 分割や新しいタブで、作業していたディレクトリのままシェルを始める

- 日付: 2026-10-22
- ストーリー: #109

## 背景

分割や新しいタブ（Workspace）で増やしたターミナルは、Accompany を起動したディレクトリでシェルを始めていた。作業しているディレクトリで続きを開くには、毎回 cd し直す必要があった。

## 決定

- **どのディレクトリか**: 分割は分割元のターミナル、新しいタブは自分がフォーカスしているターミナルの、前面のプロセスのカレントディレクトリ。前面のプロセスはエージェントの判別（[ADR 70](70-agent-detection.md)）と同じく ps の tpgid で調べ、プロセスグループのリーダー（pid がグループの番号と同じもの）のカレントディレクトリを見る。分からなければシェル（ターミナルで起動したコマンド）自身のカレントディレクトリを見る
- **調べ方**: Linux は `/proc/<pid>/cwd` の readlink、macOS などは `lsof -a -p <pid> -d cwd -Fn`。lsof はシェルを通さずに動かし、2 秒で打ち切る。時間の上限付きで動かす処理は、ps と共通にする（`command-output.ts`）
- **分からないとき**: 調べたパスを stat し、ディレクトリとして存在するときだけ使う。調べられない、プロセスが終わっている、削除されている（Linux の readlink は「 (deleted)」を付けて返す）ときは、Accompany を起動したディレクトリで始める。調べてから起動するまでに消えて `Bun.spawn` が失敗したときも、起動したディレクトリで起動し直す
- **自分がフォーカスしているターミナル**: キーボードショートカットでは、キー入力の先のターミナルの ID をブラウザが送る。サイドメニューの「新しい Workspace」では、サーバーが持っている、その参加者が最後にフォーカスしたターミナルを使う。どちらもなければ（フォーカスしたことのない参加者）、起動したディレクトリで始める
- **調べている間の変化**: 分割は、調べ終えてから分割元のタブとターミナルを探し直し、なくなっていたらターミナルを作らずに戻る。新しいタブは、調べている間にフォーカスしていたターミナルが閉じられても、調べたディレクトリで開く（頼まれた操作なので捨てない）

## 理由

- **前面のプロセスを見る理由**: シェルから別のディレクトリで動くコマンド（サブシェルやエージェントなど）を動かしているときは、そのコマンドが作業している場所で続きを開きたいことが多い。前面がシェルのときは、シェル自身を見るのと同じになる
- **グループのリーダーを見る理由**: ps の出力から前面のプロセスを 1 つ選ぶ必要がなく、エージェントの判別で使っている ps の結果（pgid）だけで済む
- **ショートカットで ID を送る理由**: フォーカスの移動を送った直後にショートカットを押すと、サーバーにフォーカスが届く前に新しいタブの要求が届くことがある。キー入力の先はブラウザが確実に知っている

## 影響・今後の課題

- 分割と新しいタブは、ターミナルを作る前に ps と lsof の分だけ（通常は数十ミリ秒、最長で数秒）待つ
- 再起動で戻したターミナル（[ADR 34](34-session-restore.md)）は、これまでどおり起動したディレクトリで始める。前回のカレントディレクトリは保存していない
- `SHELL` が相対パスのときは、カレントディレクトリが変わるとシェルが見つからず、起動したディレクトリで起動し直す
