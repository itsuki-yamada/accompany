# 端末の大きさは一番小さい表示領域に合わせ、ウィンドウの大きさで持つ下限を設ける

- 日付: 2026-10-21
- ストーリー: #99
- docs/adr/51-largest-size.md の「端末の大きさは参加者のうち一番大きい表示領域に合わせる」を置き換える

## 背景

#51 から、端末（PTY）の大きさは参加者のうち一番大きい表示領域（フル HD まで）に合わせ、表示領域の小さい人はスクロールか縮小で見ていた。VS Code の隣に Accompany を細長く出すような、画面の小さい人がいると、その人はいつもスクロールか縮小をすることになり、苦労していた。

ペアプロが前提の道具なので、いま操作していない人もすぐ操作する側になる、と考える。基準と下限は、ユーザーと相談して次のように決めた（Issue #99 の本文）。

- 端末の大きさは、そのターミナルにつながっている参加者のうち、一番小さい表示領域に合わせる。ページを見ていない参加者も含める
- 極端に狭い人に全員が引きずられないよう、下限を設ける。下限より小さい参加者は、これまでどおりスクロールか縮小（と、#68 の自動の拡大）で見る
- 下限の既定は、フル HD を縦に 4 つに分けた 1 つ分（横 480 × 縦 1080 ピクセル）。縦につぶれるのは避けたいので、横に 4 つ並べる分け方にする
- 下限は人が設定でき、全員に効き、再起動しても残る

このほかに、次のことを決める必要があった。

- 下限を列数・行数で持つか、ピクセルで持つか。参加者ごとにフォントの大きさが違い、サーバーは列数・行数しか知らない
- 480×1080 を何の大きさとみなすか（ターミナルの表示領域か、ウィンドウか）
- 下限をどこで掛けるか（サーバーかブラウザか）
- 設定の置き場所と、#51 の上限（フル HD、512 列・256 行）との関係
- E2E で、テストの画面（1280×720）より大きい既定の下限をどう扱うか

## 検討した選択肢

### 下限の持ち方と、480×1080 の解釈

1. 表示領域を 480×1080 とみなし、既定のフォント（15px）で収まる列数・行数を決め打ちにして、サーバーが列数・行数で持つ（約 51 列 × 67 行）
2. 480×1080 をウィンドウの大きさとみなし、ブラウザの枠と Accompany のバーの分として決め打ちの量（およそ 150〜160px）を引いて、列数・行数を決め打ちにする（約 51 列 × 57 行）
3. 下限をウィンドウの大きさ（ピクセル）のまま持ち、各ブラウザが、自分のブラウザの枠と Accompany のバーの実寸、自分のフォントの大きさで、列数・行数に直す

### 下限を掛ける場所

1. サーバーが、参加者から届いた列数・行数の最小に、下限の列数・行数を掛ける
2. 各ブラウザが、自分の表示領域に入る列数・行数と、下限のウィンドウに入る列数・行数の大きいほうを伝え、サーバーはその最小に合わせる

### E2E での下限の扱い

1. すべてのテストの画面を、既定の下限より大きくする
2. テストのためだけの抜け道（環境変数など）で下限を外す
3. 本番と同じ経路の起動オプション `--min-window` を足し、下限を確かめるテストのほかは下限なし（`0x0`）で起動する

## 決定

- 基準: サーバー（`TerminalSession.fitToSmallest`）は、参加者から届いた列数・行数のそれぞれ一番小さいものを端末の大きさにする。ページが見えているか（#74 の visibility）では区別しない。上限（512 列・256 行、`maxSize`）は残す
- 持ち方: 選択肢 3。下限はウィンドウの大きさ `{ width, height }`（ピクセル）で持つ。既定は 480×1080。受け付けるのは 0 以上の整数で、幅 1920・高さ 1080（フル HD）までとし、0 はその向きに下限を掛けない
- 掛ける場所: 選択肢 2。各ブラウザ（`Pane.sendSize`）が、次の 2 つの列数・行数を、向きごとに大きいほうを伝える
  - 自分の表示領域（フル HD まで）に、設定したフォントの大きさで入る列数・行数（#51 と同じ）
  - 下限のウィンドウで Accompany を開いたときの表示領域に入る列数・行数。表示領域は、下限のウィンドウの大きさから、ブラウザの枠（`window.outerWidth/outerHeight` と `innerWidth/innerHeight` の差）、Accompany のツールバーとペインのバー（横はペインの枠）の実寸を引いて求める。サイドメニューは引かない
- 設定: 下限はサーバー（`Workspace.minWindow`）が持ち、参加したときと変わったときに、ワークスペースの接続で全員に配る（`min-window`）。変更は `set-min-window` で受け付け、範囲外や整数でない値は無視する。画面の配置などと同じ保存ファイル（session-store）に `minWindow` として保存し、次に起動したときに戻す。下限を保存する前の版のファイルは、既定の下限で読む
- 画面: ⚙（表示の設定）の中に、自分だけの設定と線で分けて「端末の大きさの下限」の欄（ウィンドウの幅・高さ）を置く。全員に効き、Accompany に保存することを書く。入力欄を離れたときに、範囲内の整数なら送り、範囲外なら使っている値に戻す
- 起動オプション: `--min-window <幅>x<高さ>` で下限を指定できる。保存した下限より優先する。読めない値なら、起動せずにエラーにする
- E2E: 選択肢 3。`startAccompany` は、既定では `--min-window 0x0` を付けて起動する。下限を確かめるテスト（`min-window.spec.ts`）は付けずに起動し、既定の下限・設定の画面での変更・保存を確かめる。下限より小さい人の見え方（スクロール・縮小・自動の拡大）を確かめるテストは、必要な下限を `--min-window` で渡す

## 理由

- 一番小さい人に合わせる: 画面の小さい人も、スクロールや縮小をせずに全体を見られる。画面の大きい人は、端末の周りが余白になるだけで、表示は崩れない（余白は #51 と同じく、ターミナルの背景色で塗る）
- ページを見ていない人も含める: ペアプロでは、見ていない人もすぐ操作する側になる。見ているかどうかで大きさを変えると、タブを切り替えるたびに全員の画面で描き直しが起き、戻った人の画面ははみ出す
- ピクセルで持ち、ブラウザで直す（選択肢 1・2 をやめた理由）: 列数・行数の決め打ちは、1 文字の大きさ（OS やフォントで変わる。手元の Chromium の 15px でも幅 7.5px）と、ブラウザの枠の大きさ（OS・ブラウザ・ツールバーの出し方で変わる）を仮定することになる。仮定が外れると、下限のウィンドウの人自身がはみ出す。選択肢 1 では、ターミナルの表示領域が 1080px の高さになることはまずないので、フル HD の人も含めてほぼ全員が常に縦にはみ出す。選択肢 2 は引く量の決め打ちが残る（ユーザーの指摘を受けて 2 から 3 に変えた）。各ブラウザは自分の枠の実寸とフォントの大きさを測れるので、ピクセルのまま配って各自で直せば、決め打ちが要らず、参加者ごとのフォントの大きさの違いも各自で吸収できる。下限のウィンドウちょうどの人は、下限と自分の表示領域が同じになり、はみ出さない
- ブラウザで掛ける: 列数・行数への直し方は参加者ごとに違うので、サーバーでは掛けられない。サーバーは今までどおり列数・行数だけを受け取り、最小を取るだけにする
- サイドメニューを引かない: 狭いウィンドウでは、サイドメニューは最初から隠す（docs/adr/72-sidebar.md）。下限のウィンドウ（幅 480）で使うときも隠しているとみなす
- 分割しているとき: 下限は「ターミナル 1 つがウィンドウを占めるとき」の大きさとして、ペインごとに掛ける。分割した枠が下限より小さい人は、#68 の自動の拡大で見る。分割で下限を割ると、ペアの相手の端末まで細くなり、操作する側になったときに困るため
- フル HD までにする: 各参加者の表示領域はフル HD までとみなす（#51）ので、それより大きい下限は、誰の表示領域にも収まらない大きさになるだけで意味がない
- 設定をサーバーに置く: 全員に効く設定なので、ほかの参加者にも配り、再起動しても残す必要がある。よく使うコマンド（#35）と同じく、サーバーが持って配り、同じファイルに保存する。配色・フォントの大きさのような自分だけの設定（#36）とは違うので、同じ画面に置きつつ線で分け、注記を変える
- 入力欄を離れたときに送る: 入力のたびに送ると、「1080」を打つ途中の「1」「10」で、全員の端末が小さくなって描き直しが起きる
- 起動オプションで E2E の下限を外す: テストの画面（1280×720）は既定の下限（高さ 1080）より低く、下限のまま起動すると、#99 と関係のないテストでも縦にはみ出し、分割すると自動の拡大が働く。すべてのテストの画面を大きくするのは変更が大きく、テストのためだけの抜け道は本番の振る舞いと離れる。起動オプションは本番でも使える経路（チームで下限を決めて起動するなど）で、保存ファイルと同じ値を受け付ける

## 影響・今後の課題

- フル HD の画面でも、ターミナルの表示領域は 1080px より低いので、既定の下限（高さ 1080 のウィンドウ）なら縦の行数は全員に収まる。1280×720 のような低い画面の人は、縦にはみ出してスクロールか縮小で見る（下限を下げれば収まる）
- 下限は、各ブラウザが自分のブラウザの枠を測って直すので、ブラウザの枠の大きさ（ツールバーの出し方など）やフォントの大きさが違う人どうしでは、同じ下限でも列数・行数が少し違う。サーバーは最小を取るので、端末はそのうち一番小さいものになる
- ブラウザの枠の大きさが変わる（ブックマークバーを出すなど）と、表示領域の大きさも変わるので、端末の大きさを伝え直す。ウィンドウの位置だけが変わったときは伝え直さない
- 一番小さい人がウィンドウを大きくしたり抜けたりすると、ほかの全員の端末も大きくなる（描き直しが起きる）。これは #51 で一番大きい人が変わったときと同じ性質
- docs/adr/68-zoom.md の自動の拡大は、ほかの参加者の画面が大きいときではなく、自分の枠が下限より小さいときに働くようになる。拡大中も元の分割の枠の大きさを伝える（68 の決定）のは変わらない
- `--fresh` で起動すると、保存した下限も戻さず、既定（または `--min-window`）の下限で始める

## 含めないもの

- 参加者ごとに違う下限（全員に効く設定として 1 つにする）
- ページを見ているかどうかで基準から外す仕組み
- 下限を列数・行数で直接指定する入力（ウィンドウの大きさのほうが、人が決めやすい）
