# ほかの参加者の選択範囲を見せる

- 日付: 2026-10-20
- ストーリー: #94

## 背景

ペアプロで「ここ」と指し示すのに、ターミナルの選択範囲が相手にも見えると便利。利用者からは「以前は選択範囲も相手に見えていたが、いまは見えなくなっている」と報告があった。選択範囲は、#93 のペアプロモード（フォロー）でなくても見えるようにしたい。

### 「以前は見えていた」件の調査

まず、Accompany の変更でマウスの押下・ドラッグがアプリに届かなくなった経路がないかを `git log -S` で追った。

- ブラウザでマウスの押下を止めているのは 2 か所だけ。右クリック（#43、Accompany のメニューを出すため）と、マウスの報告モードが有効なときのリンクの上での押下（#60、docs/adr/59-single-link-open.md）。リンクの上から始めたドラッグはアプリに届かないが、それ以外のドラッグは届く
- `index.ts` の `pointerdown`（#71 のフォロー）や分割の境界のドラッグは、端末への押下を止めていない
- xterm.js（6.0.0）は #14 から上げていない

一方で、偽のアプリ（`e2e/fixtures/mouse-reporter.ts`、Claude Code と同じく `?1000h` `?1002h` `?1006h` を有効にして、受け取った入力を表示する）で確かめると、**途中から参加した人のドラッグがアプリに届かない**ことが分かった。

- サーバー側の画面の書き出し（`@xterm/addon-serialize`）は、マウスの報告モード（`?1000h` / `?1002h` / `?1003h`）は含めるが、報告の形式（SGR の `?1006h`）を含めない
- そのため、途中から参加した人（ページの再読み込み、Workspace の切り替えでつなぎ直した人、#56 の再起動のあとに開いた人も）のブラウザは、従来の形式（`ESC [ M ...`）で報告する
- xterm.js は従来の形式の報告を `onData` ではなく `onBinary` で出す。Accompany は `onData` だけを送っているので、アプリには何も届かない

本物の Claude Code（2.1.303 / 2.1.304、全画面の表示）でも確かめた。

- 全画面の表示では `?1000h` `?1002h` `?1003h` `?1006h` を有効にし、ドラッグを自分で受け取って、選択範囲を自分の出力として描く（出力なので全員に見える）。範囲を選ぶとクリップボードにもコピーする（「copied N chars to clipboard」）
- Claude Code は、フォーカスが外れた報告（`ESC [ O`）や端末の大きさの変更（SIGWINCH）のたびにマウスのモードを出し直す。そのため、上の不具合があっても、たいていはすぐに SGR 形式に戻り、途中から参加した人のドラッグも届いていた（直す前のコードでも、途中から参加した人のドラッグで Claude Code が選択範囲を描いた）
- 確かめている途中で、Claude Code が「Claude Code's fullscreen renderer didn't finish starting last time on this machine, so this launch is using the classic renderer」と出し、従来の表示（classic renderer）で起動したことがあった。従来の表示はマウスの報告モードを有効にしないので、ドラッグは xterm.js がブラウザの中だけで選択し、ほかの参加者には見えない

以上から、「以前は見えていたのに、いまは見えない」は、Accompany の変更ではなく、Claude Code の表示のしかた（全画面の表示か、従来の表示か）による可能性が高いと考える。全画面の表示ではドラッグを Claude Code が描くので全員に見え、従来の表示（設定、または全画面の表示の起動に失敗したときの切り替え）では各参加者のブラウザの中だけの選択になる。ただし、SGR 形式を戻していない不具合は Accompany 側のものなので、合わせて直す。

## 検討した選択肢

1. 選択範囲をどう配るか
   - A. 配置の WebSocket の presence（参加者の一覧）に、参加者ごと・ターミナルごとの選択範囲を持たせて配る
   - B. ターミナルごとの WebSocket で配る
2. 位置の表し方
   - A. スクロールバックを含めたバッファの行（絶対行）と列
   - B. 表示領域の中の行と列
   - C. 出力の始めからの行の番号（バッファの行に、スクロールバックから押し出された行の数を足したもの）と列
3. 描き方
   - A. xterm の decoration API（`registerDecoration`）で描く
   - B. 端末の画面（`.xterm-screen`）の上に自前の層を置いて描く。行の位置は xterm の marker（`registerMarker`）で覚える
4. 1 人が複数のターミナルで選択しているとき
   - A. 参加者ごとに 1 つだけ（最後に選択したもの）
   - B. ターミナルごとに持つ（xterm は、ターミナルごとに選択範囲を残す）

## 決定

1 は A、2 は C、3 は B、4 は B を採る（2 は、はじめ A を採ったが、レビューで C に改めた。下の「スクロールバックがいっぱいのとき」を参照）。

- ブラウザは xterm の `onSelectionChange` で `getSelectionPosition()` を読み、変わったら `{ type: "select", terminal, start, end }` を送る。選択をやめたとき（範囲なし）と、ターミナルを抜けたとき（Workspace の切り替えやターミナルを閉じたことで、ペインがなくなったとき）は、`start` と `end` なしで送る
- サーバーは参加者（`Member`）の `selections`（ターミナルの ID → 範囲）に持ち、presence で全員に配る。参加者が抜けると、presence からその人ごと消える
- 行は、出力の始めからの行の番号で送る。各ブラウザとサーバー側の画面が、スクロールバックから押し出された行の数を数え（xterm の内部の API。`src/trimmed-lines.ts`）、バッファの行に足す。途中から開いたターミナルには、サーバーが画面の書き出しの前に、それまでに押し出した行の数を送り、ブラウザはそこから数え始める。代替画面にはスクロールバックがないので、バッファの行をそのまま使う
- スクロールバックの行数（1000 行）は、サーバー側の画面とブラウザの端末で同じ定数（`src/scrollback.ts`）を使う
- ブラウザは、出力を書き終えるたび（`onWriteParsed`）にも自分の選択範囲を読み直し、変わっていれば送り直す（重なったものは送らない）。選択した行が押し出されて xterm の選択がなくなったことを伝えるため
- サーバーは、列が 0〜512（端末の列数の上限）、行が 0 以上の整数で、始まりが終わりより後ろでなく、範囲の行の数がバッファ（スクロールバック + 端末の行数の上限 256）に収まるものだけを受け付ける。範囲を新しく持つのは、あるターミナルに対してだけ。ターミナルを閉じたら、全員のそのターミナルでの範囲を消す（ブラウザも抜けたと伝えてくるが、伝え返さない参加者の分を残さないため）
- 受け取ったブラウザは、自分以外の参加者の範囲を、その人の色の半透明（35%）と下線で、文字の上に重ねて描く。マウスの操作は下の端末に通すので、相手の選択範囲の上でも自分で選択・コピーできる
- 行の位置は、受け取ったときに xterm の marker を置いて覚える。出力でスクロールバックが押し出されても、marker が同じ行についていく。描く位置は、描き直しのたび（`onRender`: スクロール、出力、フォントの大きさの変更）に計算し直す。参加者の情報が届いたときは、範囲が変わった参加者の分だけ置き直す
- 途中から開いたターミナルは、最初に届く現在の画面（スクロールバックを含む）を書き終えてから marker を置く
- 範囲を受け取ったときと違う画面（通常の画面と、全画面の TUI が使う代替画面）を表示しているときは描かない
- 途中から参加した人に SGR 形式（`?1006h`、ピクセル単位の `?1016h`）を戻す。サーバーが、カーソルの表示・非表示と同じく、出力を見て形式を覚え、書き出した画面のあとに付ける

## 理由

- 1: presence はフォーカス先と同じく「参加者がいま何をしているか」で、参加者が抜けたときに消える仕組みもそのまま使える。ターミナルごとの WebSocket は出力と端末の大きさだけを流していて、参加者の名前や色を持っていない。サーバーに足すのは、受け付けと検証だけで済む
- 2: 端末の大きさは参加者全員で同じ（docs/adr/51-largest-size.md）だが、表示領域のスクロール位置は参加者ごとに違うので、表示領域の中の位置では指せない（B を採らない）。バッファの行（A）は、スクロールバックがいっぱいのときに次の問題があった（C を採る理由）
- 3: xterm の decoration は、代替画面を表示している間は要素を隠す（Claude Code の全画面の表示や vim の上で出ない）。自前の層なら、どちらの画面でも、自分の選択範囲（`.xterm-selection`）と同じ重ね方で描ける。marker は行を覚えることだけに使う
- 4: xterm は、別のターミナルをクリックしても前のターミナルの選択範囲を残す。参加者ごとに 1 つにすると、自分の画面では残っている選択範囲が、相手の画面からは消えて食い違う

### スクロールバックがいっぱいのとき

はじめはバッファの行（A）で送っていたが、レビューで次の不具合が分かった。

- スクロールバックがいっぱいになると、xterm は出力のたびに先頭の行を押し出し、選択範囲の行も詰める（`SelectionModel.handleTrim`）。ただし `onSelectionChange` は出さない。そのため、サーバーに残る行が古いままになり、途中から参加した人や、置き直したときに、押し出された行の数だけ違う行に出た（1200 行出して row 1180 を選び、11 行出すと row 1191 に出た）。選択した行が押し出されて選択がなくなっても、サーバーに範囲が残った
- 出力のたびに選択範囲を送り直しても、受け取った側の端末が出力をまだ書き終えていない（押し出しがまだ起きていない）と、やはりずれる。範囲は配置の WebSocket、出力はターミナルの WebSocket と別の経路で届き、xterm は書き込みを後回しにすることがあるので、どちらが先かは決まらない（E2E で、受け取った側が 12 行ずれて表示領域の外に出ることがあった）
- 押し出された行の数を足した行の番号なら、押し出されても変わらないので、送る側と受け取る側で書き終えた時点がずれていても、同じ文字の行を指せる。送り直しは、選択がなくなったことを伝えるためだけに残した

## 影響・今後の課題

- 選択範囲は、xterm がブラウザの中で選択したもの（ふだんのドラッグ、ダブルクリック、「すべて選択」、検索のヒット）が対象。Claude Code の全画面の表示のように、アプリがドラッグを受け取って自分で描く選択は、これまでどおりアプリの出力として全員に見える（この仕組みは通らない）
- マウスの報告モードが有効なアプリ（Codex や Claude Code など）の上でブラウザの中で選択するには、修飾キーを押しながらドラッグする。xterm.js の `macOptionClickForcesSelection: true` を有効にしており、macOS では Option (Alt) キー、Windows・Linux では Shift キーを押しながらドラッグすることで、アプリへのマウス報告をバイパスして範囲選択・コピーができる
- 押し出された行の数は、xterm の内部の API（バッファの行の一覧の `onTrim`、リセットで作り直されるバッファ）で数えている。xterm.js を上げるときは E2E（`e2e/tests/remote-selection.spec.ts`）で確かめる
- 相手と自分でバッファの中身がずれる（途中から参加した人の画面の書き出しが、元の画面と行の数が違うなど）と、少しずれた位置に出る。端末の大きさの変更で行が折り返し直されたときも、選択した人の xterm が範囲を消さない限り、元の行のままになる
- ドラッグの間は、範囲が変わるたびに送る。参加者が多くなり負荷が問題になったら、間引くことを検討する
- 選択範囲を受け取ったことはスクリーンリーダーには伝えない（描く層は `aria-hidden`）
- 従来の形式（`?1006h` などを有効にしないアプリ）の報告は、これまでどおり `onBinary` で出て送られない。そうしたアプリではマウスが使えない。困る例が出たら、`onBinary` も送ることを検討する（バイト列をそのまま PTY に書く必要がある）
- スクロール位置の共有は含めない（#93 のペアプロモードで扱う）
