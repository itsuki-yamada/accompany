# 開発プロセス

## チームと価値観

- XP と TDD の考え方を大切にする。具体的な進め方や適用範囲（テストを書くタイミングや Red、Green、Refactor サイクルを含む）は、E2E テストを除き一律に定めず、個人の判断に委ねる。

## E2E テスト

- E2E テストは必須とし、プロダクトの仕様として扱う。
- ストーリーの実装では、先に E2E テストを書いて失敗することを確認してから実装する。
- E2E テストを書いて失敗することを確認した時点で、実装より先に一旦コミットする。
- E2E テストは Playwright で書き、`e2e/` に置く。
- 人間が `main` に直接作業するときは、失敗するテストだけのコミットを push してよい。ただし、そのテストに `@wip` タグを付け、実装して通ったらタグを外す。CI の E2E は `@wip` のテストを除いて実行する。

## ブランチと作業開始

- trunk-based development を基本とし、`main` に小さく頻繁に統合する。長期間の作業ブランチを維持しない。
- 作業を始める前に共有ブランチの最新を `git pull --ff-only` で取り込む。未コミットの変更がある場合は、その内容を確認して保護してから同期する。
- エージェントのみで実装した変更は、`main` に直接積まずにプルリクを作る。プルリクには E2E の実行ログ（Red と Green）と、Playwright のスクリーンショット・動画などの証跡を貼る。

## リリース

- 触って確かめてもらうため、配布物（tarball）の中身を変えたプルリクを `main` にマージしたら、そのたびにバージョンを上げて正式な Release を出す。いくつか溜まるのを待たない。
- バージョンは `app/server/package.json` の `version` を上げるプルリクで上げる。マージされると、CI（`.github/workflows/release.yml`）が tarball の E2E を通したうえで Release を作る。
- 機能の追加ではマイナーを、修正だけのときはパッチを上げる。
- 文書やテストだけを変えたプルリクでは、バージョンを上げない。
- エージェントは、バージョンを上げるだけのプルリクを、CI が通ればマージしてよい。

## ストーリー管理

- ユーザーストーリーと進捗は GitHub Issue と [GitHub Project](https://github.com/users/itsuki-yamada/projects/6) で管理する。
- ストーリーの書き方、粒度、Project の運用方法は [story-management.md](story-management.md) に従う。

## コミットメッセージ

- Conventional Commits の形式で日本語にし、何を変更したか簡潔に分かるメッセージにする。
- 変更を独立してレビューしやすい単位に分けることを推奨する。ただし、分けるかまとめるか、コミット単位の決定はユーザーに委ねる。
- 例: `feat: ブラウザからターミナルに入力する`
- 例: `docs: 開発プロセスのルールを追加`

## ルールの見直し

- 人間の開発者は、相手の事前同意を得ずに、よりよいと考えるルールへ随時変更できる。
- エージェントは独自判断でこの文書や関連する開発ルールを変更しない。改善が必要と考えた場合は変更案を提示する。

## スキル・文書の作成とレビュー

- スキルや文書の本文は日本語を基本とし、人間が目的、意図、変更点を追ってレビューしやすい表現にする。固有名詞、標準用語、コマンド、コード識別子は必要に応じて原語表記を保つ。
- 見出しや箇条書きで情報を整理し、必要な指示・背景・例を簡潔に記す。要件と推奨、例と必須事項は区別して書く。
